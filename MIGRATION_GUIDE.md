# Migration Guide — Converting Existing Projects to Nix

This guide covers converting a non-Nix project into a reproducible Nix-based project, organized by project type.

## General Process

### Phase 1: Analysis

1. **Identify build systems**: Look for `Cargo.toml`, `go.mod`, `package.json`, `CMakeLists.txt`, `pyproject.toml`, `Makefile`, etc.
2. **Categorize dependencies**:
   - `nativeBuildInputs`: Build-time tools (compilers, code generators, `pkg-config`)
   - `buildInputs`: Runtime libraries (C libraries, system deps)
3. **Note special requirements**: GPU support, proprietary SDKs, specific kernel features
4. **Identify test framework**: How are tests run? (pytest, cargo test, go test, etc.)

### Phase 2: Scaffolding

1. Pick the closest template from this repo:
   - `nix flake init -t github:projectinitiative/golden-template#python`
   - `nix flake init -t github:projectinitiative/golden-template#rust`
   - etc.

2. Adapt the template to your project's specifics:
   - Update `pname`, `version`, `src`
   - Add project-specific inputs
   - Configure the appropriate builder

### Phase 3: Iteration

Use the fast-feedback loop:

```bash
# Work iteratively (fast, incremental)
nix develop --command <your-build-tool>

# Validate sandbox build (slow, complete)
nix build
```

**Python**: `nix develop --command python -m pytest`
**Rust**: `nix develop --command cargo build`
**Go**: `nix develop --command go build`
**Node**: `nix develop --command npm run build`

### Phase 4: Hardening

- Add `checks` for formatting, tests, and linting
- Configure a `formatter` (nixfmt, treefmt)
- Set up CI with `nix flake check && nix build`
- Add `.envrc` with `use flake`
- Create `AGENTS.md` with project-specific agent instructions

## Per-Type Migration Details

### Python → uv2nix

**Before**: `requirements.txt`, `setup.py`, or old-style `python3.withPackages`

1. **Install uv**: `pip install uv` (or via nix shell)
2. **Initialize uv**: `uv init` or `uv add` each dependency
3. **Lock**: `uv lock` to generate `uv.lock`
4. **Adapt flake.nix**: Use `uv2nix` + `pyproject.nix` pattern from the template

**Key files to create/modify**:
- `pyproject.toml` (already exists, ensure build-system is set)
- `uv.lock` (generated by `uv lock`)
- `flake.nix` (from template)

**Common pitfalls**:
- C-extensions: Use `overrideScope` to link system libraries
- Private packages: Use `FETCHCWD` or custom fetchers
- Legacy setup.py: Migrate to `pyproject.toml` first

### Rust → Crane

**Before**: `Cargo.toml`, `Cargo.lock` (already exist)

1. **Add crane input** to `flake.nix`
2. **Split build**: `cargoArtifacts = buildDepsOnly { ... }` then `buildPackage { inherit cargoArtifacts; ... }`
3. **Handle sys crates**: If using `openssl-sys`, `libgit2-sys`, etc., add `pkg-config` and system libraries

**Key files**:
- `Cargo.toml`, `Cargo.lock` (already exist)
- `flake.nix` (from template)

**Common pitfalls**:
- Git dependencies in Cargo.toml: Must be fetchable by crane
- Proc macros: Usually work fine, but may need `cargoArtifacts` tuning
- Workspace crates: Use `craneLib.buildWorkspace` for multi-crate projects

### Go → buildGoModule

**Before**: `go.mod`, `go.sum` (already exist)

1. **Set `vendorHash`**: Start with `vendorHash = "";`, build to get the hash, then set it
2. **SubPackages**: Use `subPackages = [ "." ]` or specific package paths
3. **CGo**: If using CGo, add `buildInputs` for required C libraries

**Key files**:
- `go.mod`, `go.sum` (already exist)
- `flake.nix` (from template)

### Node/JS → buildNpmPackage

**Before**: `package.json`, `package-lock.json` or `yarn.lock`

1. **Set `npmDepsHash`**: Start with `npmDepsHash = "";`, build to get the hash
2. **Build commands**: Set `buildPhase` to `npm run build` or your build command
3. **Install**: Set `installPhase` to copy output to `$out`

**Key files**:
- `package.json`, `package-lock.json` (already exist)
- `flake.nix` (from template)

### Embedded (ESP-IDF/Arduino)

**Before**: PlatformIO, manual SDK, or Arduino IDE

1. **Install esp-idf toolchain**: Use `esp-dev` flake input
2. **Handle Arduino libs**: Use `arduino-nix` for library management
3. **Vendor managed components**: Create a `nix/dependencies.nix` to prefetch

**Key files**:
- `flake.nix` (from template)
- `nix/dependencies.nix` (vendored component fetches)
- `nix/scripts.nix` (wrapper scripts for build/flash/monitor)
- `treefmt.toml` (for C++, JSON, MD formatting)

**Common pitfalls**:
- ESP-IDF version mismatch: Pin exact ESP-IDF version in inputs
- AppArmor/bubblewrap: May need workaround in CI (see NIMRS-Firmware CI)
- QEMU cross-build: May need `binfmt` support for aarch64 targets

### Container Images

**Before**: Dockerfile

1. **Use `dockerTools`**: Build image layers with Nix for reproducibility
2. **Build from flake packages**: The flake package produces a `docker load`-able image
3. **Multi-arch push**: Use `ops-utils` scripts for CI/CD

**Key files**:
- `flake.nix` (from template)
- Container definitions in `flake.nix` using `pkgs.dockerTools.buildImage`

### Dev Shell Only (No Package Build)

For projects that don't produce a build artifact (docs repos, config repos, etc.):

1. **Use `mkShell` directly**: No package derivation needed
2. **List tools explicitly**: Every tool in `packages` = []
3. **Shell hook**: Print available commands

### Nix Library

For shared Nix functions (like `ops-utils`):

1. **Export via `lib`**: The main output is `lib`, not `packages`
2. **Document functions**: Each function should have a clear signature and docstring
3. **Provide `mkUtils`**: A convenience function that instantiates all tools at once

### NixOS Configuration

**Before**: Imperative system config, Ansible, or manual setup

1. **Structure**: Use `flake.nix` with `nixosSystem` for each host
2. **Modularize**: Split into `modules/` directory by concern (networking, firewall, services)
3. **Secrets**: Use `sops-nix` or `agenix` for secret management
4. **Hardware**: Use `nixos-hardware` for known hardware configs
